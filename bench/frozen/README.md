# 冻结的参照点

评分要有参照点，参照点必须能复现。这里放两个**同一台机器、同一套 harness**
跑出来的数据点：

- `v0/` —— 改之前是什么样（最初的骨架：角度写死、没有关联、没有提前量）；
- `s1-s4/` —— 把距离、关联、提前量、生命周期都做对之后是什么样
  （`solution` 分支上的 `pipeline/` + `solver` + `tracker`）。

`reference/`（`-DBUILD_REFERENCE=ON`）是另一份独立实现，数字见下。

每个目录里都有 `report.md`、`aim-*.json`、`client-*.log`、`meta-*.json`，
所以 `python3 bench/report.py --out-dir bench/frozen/v0` 能原地重生成表，
不用重跑仿真。`s1-s4/` 里另外有 `noise-*.json`（重复跑的统计）。

## 三个数据点

8 秒、每场景一次、1440×1080、图形模式。单位是**命中/秒**（主指标）。

| 场景 | v0 | S1–S4 | 参考实现 |
|---|---:|---:|---:|
| `static` | 5.50 | **6.88** | 5.75 |
| `lowlight` | 5.75 | **6.50** | 5.50 |
| `far` | 0.00 | **9.00** | 2.50 |
| `translate` | 0.00 | **3.50** | 2.00 |
| `spin` | 0.00 | **3.62** | 2.12 |
| `combined` | 0.50 | **3.88** | 0.38 |
| `toofar` | 0.00 | 0.00 | 0.00 |

跟踪误差（云台实际指向 vs 理想弹道解，中位数，度）：

| 场景 | v0 | S1–S4 |
|---|---:|---:|
| `static` | 0.26 | 0.11 |
| `far` | 0.88 | 0.14 |
| `translate` | 3.29 | 0.82 |
| `spin` | 1.84 | 0.82 |
| `combined` | 2.63 | 0.92 |

命中落点偏差（板面内，cm）：`static` 0.7 → `far` 1.2 → `combined` 4.2 →
`spin` 4.5 → `translate` 5.0。

## S1–S4 的重复性（这次顺手量了）

`bench/noise.py <场景> --runs 3`，8 秒。原始日志在 `s1-s4/noise/`，
可以直接 `python3 bench/report.py --out-dir bench/frozen/s1-s4/noise` 复算。

| 场景 | 三次的命中/s | 平均 | 相对波动 |
|---|---|---:|---:|
| `translate` | 3.38 / 4.00 / 3.00 | 3.46 ± 0.51 | 15% |
| `spin` | 2.88 / 3.38 / 3.12 | 3.13 ± 0.25 | 8% |
| `combined` | 3.12 / 3.50 / 3.50 | 3.38 ± 0.22 | 6.5% |

九轮帧率全部 54~55，没有因饿死而失真的轮次。

比 v0 和 `reference/` 时代的 ±26%（甚至 0→1.9 那种量级）小得多。
原因不是运气：关联门限改成各向异性、开火残差门限改成按距离归一之后，
系统不再有"这一次刚好没崩"的分支。

## 为什么 S1–S4 在 `spin`/`combined` 上比参考实现高一个数量级

参考实现在关联门限失败时会**等同一块板转回来**（2.5 rad/s 下要等 2.5 s），
这段时间等于瞎了。S1–S4 是"门限失败就立刻在新板上重开一条轨，速度沿用
手上那份"——四块板装在同一台车上，刚体速度本来就是同一份。

`combined` 0.38 vs 3.88 就是这个差别，不是运动模型的差别。

## 建议的评分口径

| 项 | 依据 |
|---|---|
| 主指标 | `hit / 运行秒数`，8 秒 × 3 次取中位数 |
| 及格 | `static` 和 `lowlight` 各 ≥ **4.0**（做对是 6.9 / 6.5） |
| S1（距离 + 弹道） | `far` ≥ **1.5**（v0 0.00，参考 2.50，做对 9.00） |
| S2+S3（关联 + 提前量） | `translate` ≥ **1.0**、`spin` ≥ **1.0**（v0 都是 0，做对 3.5 / 3.6） |
| 附加 | `combined` ≥ **0.8**（v0 0.50，参考 0.38，做对 3.88） |
| 不算分 | `toofar`：检测的物理极限，只看"有没有候选" |

线画在 v0 和"做对"之间的**低段**，理由：参考实现那一档（2.0/2.1）也是
"做对了"的水平，把线画到 2 会把及格和优秀混成一档；而画在 1.0 附近能
清楚区分"有没有做出提前量"。

## 读这张表必须知道的六件事

1. **先看帧率和"仿真/墙钟"两列。** 帧率 < 40 或仿真/墙钟 < 0.95 的轮次
   直接作废——闭环带宽掉下来，命中/s 会偏低，那不是算法的问题。
   （实测踩过：有一次只有 23 帧/8 秒，我差点把它当成跟踪器的 bug。）
2. **`toofar` 的跟踪误差没有意义。** 7 m 一个候选都没有，云台停在
   yaw=0/pitch=0，那个姿态碰巧接近这个距离的理想解。
3. **S1–S4 的"检出率"列比 v0 低**（`far` 0.56 vs 1.00）。口径不同：v0 只要
   "检出一个候选"，S1–S4 还要求 PnP 成功、重投影 < 6 px、入射角 < 76°。
4. **`far` 的 9.00 已经贴着武器射速上限**（10 发/秒），再优化也只能到 10。
5. **检测耗时跨天不可比**（机器负载差 15%）。比 `hit/s`，别比 `detect_ms`。
6. **`reference/` 的数字是这台机器上新测的**，不是 `docs/stages.md` 里那份
   （那份来自另一台机器，`far` 标的是 3.00，本机 2.50）。
