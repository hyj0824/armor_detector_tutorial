# 冻结基线（v0，2026-10）

评分要有参照点，参照点必须能复现。这份是**一台机器、一次跑完、同一份二进制**
的结果，用来回答"改之前是什么样"和"我的机器上的数能不能和这份比"。

`report.md` 是 `bench/report.py` 的原样输出，`aim-*.json` 是每个场景的
`bench/truth.py` 摘要（逐 tick / 逐发明细没进仓库，太大也不必要）。

## 复现条件

| 项 | 值 |
|---|---|
| 二进制 | `solution` 分支上 v0 那一版（`pipeline.cpp` 里还是 `kFixedElevationDeg = 2.10`） |
| 场景 | `scenarios/*.cfg`，`max_health=10000` |
| 时长 | 8 秒，每场景**一次** |
| 分辨率 | 1440×1080，图形模式 |
| 命令 | `TAG=frozen-final bench/run_all.sh` |
| 采样 | `bench/sample_state.py`，80 Hz |

`bench/report.py --out-dir bench/frozen` 可以原地重新生成 `report.md`，
因为 `client-*.log` 和 `meta-*.json` 都进了仓库。

## 读这份基线必须知道的三件事

1. **动态场景的命中/s 本身抖 ±26%**（见 `bench/frozen/README.md`）。
   所以 `0.40 → 0.45` 不算改进，`0.40 → 0.65` 才够，下结论至少重复 3 次。
   静态场景抖得小：同一份二进制两次跑 `static` 得到 5.50 和 5.75（±4.5%），
   性能类结论可以单次测。
2. **检测耗时跟机器负载相关**：同一份代码在不同时间跑，`mean_detect_ms`
   在 5.4~6.2 ms 之间漂（采样器在执行时多占约 0.6 ms）。跨天比 `detect_ms`
   不可靠，比 `hit/s` 可靠。
3. **`toofar` 的跟踪误差没有意义**：7 m 一个候选都没有，云台一直停在
   yaw=0/pitch=0，而那个姿态碰巧接近这个距离的理想解。它只能说明
   "检测断了"，不能说明"瞄得准"。

## 和文档里旧数字的差别

历史文档里另外记过一组 v0 的数字（`static` 7.00、`far` 0.00），那是另一台机器、
另一天跑的，和这份差 12%。**以这份为准**；换机器就用同样的命令重测一份覆盖它。
