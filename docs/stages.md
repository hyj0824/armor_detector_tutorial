# 四个阶段：v0 缺什么、怎么自查

v0 是一个**能跑通但明显不够好**的系统。它缺的四件事不是随便挑的，
而是四个场景各自逼出来的。按场景顺序做，不要跳。

每一节的验收都要求：**同一场景连跑两次，差异要大于 2 倍标准差**（见下面的噪声基线）。

---

## 指标口径（第二重要，先看完再往下读）

评分只信仿真：`bench/run.sh` 起一个采样器把 `state.json` 落盘，
再由 `bench/truth.py` 出指标。**它不读 trace**，所以换实现、删遥测
都不会影响评分。冻结的 v0 基线在 `bench/frozen/`。

| 指标 | 定义 | 看什么 |
|---|---|---|
| 命中/s | 仿真统计的 `hit / 运行秒数` | **主指标** |
| 跟踪误差 | 逐 tick「云台实际指向 vs 理想弹道解」的中位数 | 解算 + 跟踪 |
| 落点cm | 命中落点到装甲板中心的板面内距离 | 真正的精度 |
| miss_kind | ground / body / expired 各几发 | 偏低了 / 打机身 / 飞过头 |

两个很容易搞错的点：

1. **“出膛方向 vs 装甲中心”不是误差。** 正确的弹道解故意瞄高 1.5~2.6°，
   拿直线去比会把对的判成错的。要比就和「理想弹道解」比。
2. **`mean_aim_error_deg`（指令角减云台实际角）不是精度指标。**
   它只说明“伺服跟不跟得上指令”，云台不动它也接近 0。

## 噪声基线（先读这个）

同一份二进制，同一个场景重复跑，指标本身就在抖。**不知道抖多少，就没法判断"改进"是不是真的。**

`translate` 场景重复 5 次（8 秒）：

| 跑的是 | 指标 | 平均 | 标准差 | 相对波动 |
|---|---|---:|---:|---:|
| 基线 v0 | 命中率 | 0.000 | 0.000 | —— |
| 基线 v0 | 舵机误差 | 1.368° | 0.062° | 4.5% |
| 基线 v0 | 检测耗时 | 4.588 ms | 0.185 ms | 4.0% |
| 参考实现 | 命中率 | 0.466 | **0.120** | **26%** |
| 参考实现 | 舵机误差 | 1.123° | 0.107° | 9.5% |

**结论：动态场景的命中率噪声约 26%。** 换句话说：

- `0.40 → 0.45` 这种变化，**不能**当作改进的证据；
- `0.40 → 0.65` 才勉强够；
- 想下结论，至少要重复 3 次取平均。

检测耗时就稳得多（4%），所以"性能优化"类的结论可以用单次测量。

复现：

```bash
python3 bench/noise.py translate --runs 5
ARMOR_BIN=build/armor_aim_ref python3 bench/noise.py translate --runs 5
```

## 参照点是怎么来的（第二重要的表）

三个数据点，全部在**同一台机器、同一套 harness** 上跑出来（8 秒、每场景一次）。
冻结的原始结果和复现条件在 `bench/frozen/`：

- **基线 v0** —— 最初的骨架（角度写死、没有关联、没有提前量）；
- **参考实现** —— `-DBUILD_REFERENCE=ON` 才编译的 `armor_aim_ref`；
- **S1–S4** —— `solution` 分支上的 `pipeline/ + solver + tracker`（四个阶段都做对）。

| 场景 | 基线 v0 | 参考实现 | S1–S4 | 这块是什么 |
|---|---:|---:|---:|---|
| `static` | 5.50 | 5.75 | 6.88 | 闭环通了 |
| `lowlight` | 5.75 | 5.50 | 6.50 | 检测在低曝光下没崩 |
| `far` (5.5 m) | 0.00 | 2.50 | **9.00** | **S1** 距离 + 弹道 |
| `translate` | 0.00 | 2.00 | **3.50** | **S3** 提前量 |
| `spin` | 0.00 | 2.12 | **3.62** | **S2** 关联 |
| `combined` | 0.50 | 0.38 | **3.88** | **附加题**，见下 |
| `toofar` (7 m) | 0.00 | 0.00 | 0.00 | 检测的物理极限 |

单位是 **命中/秒**（`bench/report.py` 的"命中/s"列）。
`far` 的 9.00 已经贴着武器射速上限（10 发/秒）。

> 参考实现在 `spin`/`combined` 上低一个数量级，原因是它在关联门限失败时
> **等同一块板转回来**（2.5 rad/s 下要等 2.5 s），而 S1–S4 是"门限失败就立刻
> 在新板上重开一条轨、速度沿用"。这是**关联策略**的差别，不是运动模型的差别
> ——也就是说 `combined` 并不是非得上整车估计器才能拿下。

**这两列不是分数线，是两个真实实现的数据点。** 用它们判断两件事：

- 基线是 0、参考是 3，说明这件事**能做**，你卡住的时候不是白费劲；
- 你在 0.3 而参考在 3，说明还差得远——**差在哪一层**，去第 2 节找。

### 为什么主指标是"命中/秒"而不是命中率

命中率可以被"很少开火但很准"骗过去。基线在 `translate` 上只打 21 发、
命中 0，命中率 0.00；但在某些软场景里它只打 6 发、中 4 发，命中率 0.80——
看上去比参考实现还好。**命中/秒同时惩罚"打不准"和"不敢打"**，才是有意义的指标。

### 读这张表的三个注意

1. **动态场景的重复性只有 ±30%。** 参考实现跑 `translate` 三次分别得到
   1.75 / 1.25 / 1.12 命中/秒。所以"我这次比上次高 0.2"基本不能当结论。
2. **`combined` 是附加题。** 参考实现也只有 0.38，和基线打平。
   原因是它的速度估计用滑动线性拟合，而复合运动的轨迹是摆线，线性模型失效；
   正解要估计"整车旋转 + 平移"而不是单块板。所以这一档**不要求完成**——
   想往深处走的人再做。
3. **`toofar` 不是算法问题。** 7 m 处灯条只有 2 px 宽，低于 `min_area`，
   连候选都没有。想拿下它必须先改检测，那是另一条线。

### 检测的工作区间（`bench/sweep.py` 实测）

| 距离 | 3.0 | 3.5 | 4.5 | 5.5 | 6.0 | 7.0 |
|---|---:|---:|---:|---:|---:|---:|
| 检出率 | 0.03 | 0.68 | 0.55 | **1.00** | 0.00 | 0.00 |

| 曝光 | 0.10× | 0.40× | 1.00× | 2.50× |
|---|---:|---:|---:|---:|
| 检出率 | 0.03 | 0.67 | 0.66 | 0.67 |

读法：

- **有效区间约 3.4~5.5 m**，两头都是悬崖，不是缓坡。
- 曝光从 0.4 到 2.5 几乎没影响（灯条自发光），只有压到 0.1 才崩。
  **"曝光越低越难"这个直觉只对了一小半**——先测，再下结论。
- 6 m 处灯条只有 2 px 宽，低于 `min_area`；3.0 m 处过曝白洞比形态学核还宽。

复现：

```bash

python3 bench/sweep.py exposure --values 0.1,0.4,1.0,2.5
```

## S1 · 距离

**现象**：`far`(7 m) 一个目标都没有；`static` 只在 4 m 附近命中，换个距离就开始掉。

**为什么错**：`pipeline.cpp` 里抬升角是一个写死的常数：

```cpp
constexpr double kFixedElevationDeg = 2.10;   // 只对 4 m 附近成立
```

弹丸在 4 m 飞行约 0.17 s，下坠约 0.15 m，对应 2.1°；
7 m 时需要约 3.6°，2 m 时只需要约 1.1°。常数不可能对。

**需要什么信息**：距离。

**两条合法路径**（选一条，说清代价）：

1. `cv::solvePnP` + 已知灯条几何（小装甲 135×56 mm，大装甲 230×56 mm）；
2. 用灯条视高反推：`distance ≈ fx * 灯条实际长度 / 像素长度`。

**改哪儿**：`Pipeline::estimate` 里把 `estimate.distance` 填上，
然后用它替换 `kFixedElevationDeg`（飞行时间又依赖抬升角，需要迭代几次）。

**验收**：

```bash
bench/run.sh far 8          # 命中/s 从 0.00 到 1 以上（参考实现是 3.00）
python3 bench/sweep.py distance --values 3.5,4.5,5.5
                            # 5.5 m 不应再明显差于 4.5 m
```

**陷阱**：

- 6 m 以上是**检测**的极限，不是解算的极限。先把检测搞好，别指望 PnP 救。
- 距离估错 10%，在 5 m 处只带来 0.2° 的抬升误差，肉眼看不出；在 7 m 处才开始明显。
  所以 **S1 的验收不要只看 4 m**。

## S2 · 目标关联与状态估计

**现象**：`spin` 换板 2.52 次/秒，指令每帧抖一次，一发都打不中。

**为什么错**：`Pipeline::estimate` 每帧独立地选"离画面中心最近的板"，
没有历史、没有速度、没有换板惩罚。四块板 90° 一圈，转起来就一直在抢中心。

**需要什么信息**：历史帧。

**最小可行的做法**（按顺序加，每加一步测一次）：

1. 换板惩罚：已经锁定的板，下一帧优先；
2. 预测：用上几帧的中心差分估角速度；
3. 状态估计：CV 模型 + 门限，或者直接上 EKF；
4. 只在"旧板真的丢了"时才切换，而不是"新板更近"。

**改哪儿**：`Pipeline::estimate` 的关联部分；`TargetEstimate::yaw_rate/pitch_rate` 填上。

**验收**：

```bash
bench/run.sh spin 8         # 命中/s 从 0.00 到 0.5 以上（参考实现是 1.50）
bench/run.sh static 8       # 不能把已经满分的场景做坏
```

**陷阱**：

- 换板次数不是越低越好。目标真的转到背面时必须换，**卡死在一块板上会彻底跟丢**。
- 别忘了 `combined`：S2 在平移下也要稳。

## 附加题 · `combined`（不要求完成）

平移和自转同时发生。参考实现也只能做到 0.38 命中/秒，和基线打平——
因为它的速度估计是滑动线性拟合，而复合运动的轨迹是摆线。

想拿下它，要换运动模型：不估单块板，而是估"整车角度 + 角速度 + 平移速度"。
这就是 sp_vision 里"整车估计器"在做的事。

基线 0.38，参考实现 0.38。**到这里还能往上走，就是真的摸到门了。**

## S3 · 提前量

**现象**：`translate` 命中 0 发，误差方向稳定（总是落后）。

**为什么错**：指令瞄准的是"目标现在在哪"，但弹丸飞 0.17 s 才到，
这期间靶车已经移动了 1.5 × 0.17 ≈ 0.26 m——比装甲宽度（0.135 m）还大。

**需要什么信息**：距离（S1）+ 角速度（S2）+ 弹速与发射延迟（`state.weapon`）。

**做法**：解一个不动点。

```text
飞行时间 t = f(距离, 抬升角)
预测位置   = 当前 + 速度 * (t + 发射延迟)
t 又依赖预测位置……
迭代几次就收敛。
```

**改哪儿**：`Pipeline::estimate` 之后、`Pipeline::command` 之前，加一层预测。

**验收**：

```bash
bench/run.sh translate 8    # 命中/s 从 0.00 到 0.5 以上（参考实现是 1.12）
bench/run.sh combined 8     # 附加题：0.8 以上说明真的想清楚了
```

**陷阱**：

- 提前量必须用**同一帧**的观测时间，不要混用"最新状态"的时间戳。
- 弹速和延迟从 `state.weapon` 读，别写死——仿真里可调。

## S4 · 生命周期

**现象**：这条不用注入故障，直接能测出来——

> 把云台转到完全看不到目标的地方（比如手动改 `scenarios/static.cfg` 里的
> `center` 到 20 m），看它会不会**继续按上一条指令发 `fire=true`**。

会的。`app/main.cpp` 收到不到新帧时会一直重发 `last_command`，
而 `last_command` 里的 `fire` 是上一次算出来的。这在真机上就是"丢失目标后继续开火"。

同样的问题还有三种形态：

| 场景 | v0 的行为 | 应该的行为 |
|---|---|---|
| 丢帧 / 断流 | 一直重发旧指令 | 超过 N ms 没有新观测就 `control=false, fire=false` |
| 仿真暂停 | 同上 | 同 |
| 仿真重启（`session_id` 变了） | 继续发旧 seq | 重置 seq、丢弃旧目标 |

**需要什么信息**：时间、会话标识、观测年龄。

**改哪儿**：`app/main.cpp` 的主循环 + `io/sim_capture.cpp` 的状态传递。

**验收**：

```bash
# 1. 目标消失后必须停火
./build/armor_aim --fire --no-gui --duration=10
#    （运行中把仿真暂停 / 用极远靶位）

# 2. 重启仿真后客户端不能继续用旧会话
#    （Ctrl+C 掉仿真，再启动，看客户端是退出还是报错而不是继续发）

# 3. 有效帧率不能塌
python3 bench/noise.py static --runs 3     # frames 不应明显下降
```

**陷阱**：

- 超时时间不能拍脑袋。仿真的指令看门狗是 **250 ms**，你的观测超时必须**小于**它。
- 暂停期间**不能**复用旧目标恢复控制，必须等新观测。

## 做完之后

`bench/report.py` 会把所有跑过的场景汇总成一张表，直接贴进报告：

```bash
python3 bench/report.py
python3 bench/report.py --format=csv --save=out/report.csv
```

四个阶段各自的 bench 输出、每次改动前后各一组，就是你实验记录的全部素材。
